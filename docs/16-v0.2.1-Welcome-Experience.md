# v0.2.1 - Welcome Experience

**Status:** In Progress
**Target:** v0.2.1

**Current Development Version:** v0.2.1-0

## Phase 1 Scope

v0.2.1 begins with a UI-only first-launch Welcome Experience.

Implemented in Phase 1:

* Persisted `firstRun` flag in existing settings.
* New installs show onboarding when `firstRun` is true.
* Existing users with older settings bypass onboarding.
* Completion sets `firstRun` to false and opens the normal chat UI.
* Settings includes "Run Welcome Again..." for testing.
* Onboarding stays inside the main application window.
* Eight framework pages exist: Splash, Welcome, System Check, Ollama, Model Selection, Personalization, Features, and Finish.
* Placeholder pages do not perform system detection, installation, downloads, model changes, or settings logic.
* Placeholder copy uses Nova's calm, local-first voice rather than traditional installer language.

## Phase 2 Scope

Phase 2 replaces the System Check placeholder with a real local assessment.

Implemented in Phase 2:

* Typed Rust/Tauri `run_system_check` command.
* React reads structured backend data only; it does not inspect system information directly.
* System Check collects operating system, operating system version where available, CPU name, logical CPU count, total memory, available memory, GPU names where available, available disk space for Aether's data location, and architecture.
* Results stay local and are not sent over the network.
* The UI supports checking, complete, partial, and failed states.
* The Retry action reruns the local check.
* Missing fields do not fail the entire check.
* Failed checks show a clear friendly message, with raw details limited to Developer Mode.
* System Check copy uses Nova's calm, local-first voice and does not recommend model sizes.

## Phase 3 Scope

Phase 3 replaces the Ollama placeholder with a real local runtime check.

Implemented in Phase 3:

* Typed Rust/Tauri `check_ollama_status` command.
* Typed Rust/Tauri `start_ollama` command for a safe direct start attempt when an executable is detected.
* React reads structured backend data only; it does not inspect local processes, paths, or runtime details directly.
* Ollama checks detect, where practical:
  * whether an Ollama executable or installation appears to exist
  * whether the local Ollama API is reachable
  * the running version
  * whether local models are installed
  * installed model count and model names
* Runtime checks use the existing Ollama provider path for local model discovery.
* Checks use short bounded timeouts so onboarding remains responsive.
* Missing version or model details become a partial state rather than a total failure.
* The UI supports checking, ready, no-model, installed-but-not-running, not-installed, partial, and failed states.
* Users can continue when Ollama is reachable.
* Users can explicitly choose "Set Up Later" when Ollama is not reachable.
* The download action opens Ollama's website but does not download or install anything.
* Raw error details are shown only when Developer Mode is enabled.
* Long version strings and model names wrap inside the welcome card without widening the application window.

## Phase 4 Scope

Phase 4 replaces the Model Selection placeholder with a guided first-model experience.

Implemented in Phase 4:

* Typed Rust/Tauri `model_selection_state` command.
* Typed Rust/Tauri `start_model_download`, `cancel_model_download`, and `verify_model` commands.
* Model recommendations are loaded from `src-tauri/model-recommendations.json` rather than hardcoded in onboarding UI logic.
* The bundled recommendation catalog contains:
  * one recommended model
  * display title
  * recommendation description
  * optional detail text
  * ordered alternatives
* The current recommended model is `qwen3:8b`, displayed as "Qwen3 8B".
* Future releases can update the recommended model by changing the configuration file instead of rewriting onboarding behavior.
* If local models already exist, onboarding lists them and allows the user to select one without downloading.
* If the saved default model is installed, it remains selected.
* If the saved default model is unavailable, onboarding falls back to the first installed local model.
* If no models are installed, Nova presents the configured recommendation prominently and alternatives below it.
* Model downloads use the existing local Ollama integration and stream progress through a Tauri event.
* The UI displays percentage when available, plus estimated speed, remaining size, and time when Ollama provides byte counts.
* Downloads can be cancelled, returning the user to the selection screen.
* Failed downloads show recovery actions without leaving onboarding in a broken state.
* After a download completes, Aether automatically verifies the model with a tiny streaming prompt.
* The user can continue only after an existing model is selected or a downloaded model verifies successfully.
* Raw download and verification details remain limited to Developer Mode.
* Long model names and progress text wrap within the welcome card.

## Deliberately Deferred

The following remain outside Phase 4:

* Silent Ollama installation.
* Personalization settings logic.
* Features page setup logic.
* Finish page enhancements.
* Provider configuration beyond checking the local Ollama runtime.

## Platform Limitations

System Check is best-effort and platform-dependent:

* GPU detection is currently Windows-specific and may be unavailable on other platforms.
* Operating system version availability depends on what the host platform exposes.
* Available memory and available disk space can change while Aether is running.
* Aether avoids collecting sensitive identifiers such as serial numbers, usernames, MAC addresses, IP addresses, and device IDs.

Ollama detection is also best-effort:

* Installation detection checks known executable locations and the process PATH. Some custom installs may not be detected.
* Starting Ollama is attempted only through a direct process launch with fixed arguments. Aether does not pass user-controlled strings to a shell.
* The UI does not expose executable paths, usernames, environment paths, or unrelated process details.
* Version and model details depend on the local Ollama API responses.
* Aether only talks to the local Ollama API endpoint. No Ollama status information is sent elsewhere.

Model setup limitations:

* Download progress depends on the local Ollama pull stream. Some fields, such as speed or estimated time, may be unavailable until byte counts are reported.
* Download pause is not shown because the current Ollama integration does not support pausing a pull.
* Verification checks that the model can stream a tiny setup response through the existing provider path. It does not benchmark quality or recommend model sizes.
* Recommendation data is bundled locally. Aether does not fetch a remote model catalog.

## Definition of Done

Phase 1 is complete when:

1. First-run users see the Welcome Experience.
2. Existing users launch directly into the normal chat UI.
3. Completing onboarding persists `firstRun: false`.
4. Settings can reset onboarding with "Run Welcome Again...".
5. Back and Next navigation work across all eight pages.
6. The flow remains responsive and visually consistent with Aether.
7. The implementation avoids real setup behavior beyond the `firstRun` flag.
8. System Check reports available local device information through the backend command.
9. System Check handles missing fields and failures without blocking onboarding.
10. Ollama status reports local installation, reachability, version, and installed model details where available.
11. Ollama setup allows reachable users to continue and unreachable users to explicitly set up later.
12. Ollama setup does not install Ollama, download models, recommend models, or select a default model.
13. Model Selection reads recommendation data from configuration rather than hardcoded UI logic.
14. Model Selection supports existing installed models without downloading.
15. Model Selection can download, cancel, retry, and verify a first model through the local Ollama integration.
16. Model Selection blocks ordinary continuation until an existing or verified model is ready.
