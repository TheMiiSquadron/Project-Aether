# v0.2 — Conversation History

**Status:** Released
**Target:** v0.2.0

**Released Version:** v0.2.0

## Implementation Progress

Completed so far:

* SQLite-backed conversation storage foundation.
* Schema version tracking.
* Structured saved conversation and message records.
* Ordered messages with roles, timestamps, active model, metadata, and completion/cancel/failure/partial states.
* Active conversation load/save commands behind the Tauri backend boundary.
* UI auto-save and reload for the active conversation.
* Confirmed clear-current-conversation action.
* Multiple saved conversations.
* Conversation sidebar.
* New chat.
* Selecting an existing conversation.
* Rename conversation.
* Delete conversation with confirmation.
* Export current conversation as Markdown.
* Basic local conversation search across titles and saved message content.

Remaining before v0.2.0:

* None. Released after Windows/Envy validation.

## Mission

Aether v0.2 makes conversations persistent, organized, searchable, and recoverable.

v0.1 proved that Nova can hold a polished local conversation. v0.2 makes those conversations durable enough to matter over time.

## Product Goal

The user should trust that important conversations with Nova will survive normal app use and remain easy to find later.

The guiding question for v0.2 is:

> Can Alex return to a previous Nova conversation and continue working without friction or fear of losing it?

## Included Scope

### 1. Saved Conversations

Aether saves conversations locally and reloads them after restart.

Saved data should include:

* Conversation ID.
* Title.
* Created timestamp.
* Updated timestamp.
* Active model or last-used model.
* Ordered messages.
* Message roles.
* Message timestamps.
* Message states such as complete, cancelled, failed, or partial.
* Minimal metadata needed for future migration.

### 2. Conversation Sidebar

Aether adds a simple conversation list without turning the app into a dashboard.

The sidebar should support:

* New chat.
* Recent conversations.
* Selecting an existing conversation.
* Renaming a conversation.
* Deleting a conversation with confirmation.

The sidebar should remain quiet and secondary. The conversation stays visually primary.

### 3. Conversation Titles

Conversations need readable titles.

The first v0.2 title strategy can be simple:

* Use the first user message as the initial title.
* Trim long titles.
* Allow manual rename.

Model-generated titles can be explored later if the simple version feels insufficient.

### 4. Search

Aether should support basic local search across saved conversations.

Search should cover:

* Conversation titles.
* Message text.

Search does not need semantic search, embeddings, memory retrieval, or advanced filters in v0.2.

### 5. Storage Foundation

v0.2 introduces persistent conversation storage.

SQLite is the preferred direction because conversations are structured, searchable, and likely to grow over time. The implementation should remain behind Aether's Storage boundary so the UI and Conversation Engine do not depend directly on database details.

Storage should be designed with future migration in mind.

### 6. Migration and Backup Mindset

v0.2 does not need a complete backup system, but it should avoid choices that make future backup, restore, export, or migration difficult.

Storage decisions should favor:

* Clear schema ownership.
* Versioned migrations.
* Recoverable failure behavior.
* Avoiding opaque data formats where practical.

### 7. Export Current Conversation

Aether should allow exporting the current conversation as Markdown.

This is intentionally smaller than full backup/import. It gives the user an immediate way to preserve or share an important conversation outside Aether.

## Deliberately Deferred

The following remain outside v0.2:

* Long-term memory.
* Tool calling.
* General file access.
* Coding actions.
* Portal integration.
* Multi-device sync.
* Agents.
* Automation.
* Semantic search.
* Cross-device conversation sync.
* Full backup and restore UI.

## Definition of Done

v0.2 is complete when:

1. Conversations survive app restart.
2. No messages are lost when Aether closes normally.
3. Failed, cancelled, and partial generations are saved with clear states.
4. Deleting a conversation requires confirmation.
5. Renaming and switching conversations do not silently interrupt active generation.
6. Storage errors are shown clearly and do not corrupt existing conversations.
7. Aether remains responsive with a reasonable number of saved conversations.
8. The current conversation can be exported as Markdown.
9. Saved conversations can be searched locally by title and saved message content.
10. Empty or whitespace-only search restores the normal recent-conversation list.

## Design Notes

Conversation history is not memory.

A saved conversation is a record of what happened. Memory is a future system that decides what Nova should remember across contexts. v0.2 should not blur those concepts.

The user should feel that conversations are safe, but Nova should not yet infer long-term facts or preferences from them automatically.

## Architecture Notes

v0.2 should extend the existing architecture:

```text
UI -> Conversation Engine -> Storage
```

The UI should render conversation state and send user actions. It should not own persistence rules.

The Conversation Engine should coordinate active conversation state and generation lifecycle.

The Storage layer should own persistence details, migrations, and data loading/saving.

SQLite can be introduced here, but it should remain an implementation detail behind Storage.
